### 480GB SATA TLC SSD QoS 异常 FA 分析报告

基于目前提供的测试配置和异常数据，我整理一份偏工程化的 FA 分析。这里不急于认定 NAND、FW 或主机接口存在缺陷，而是从现象、机理、可能根因和验证路径几个方面展开。

先给出总体判断：目前最值得怀疑的是 SSD 在特定 Host IO Size 和高并发条件下的内部请求处理与 NAND 调度效率，持续写入带来的 Fold、GC 等后台操作可能进一步放大长尾延迟。

现阶段还没有足够证据将问题归因于 3KB 非对齐写入、RMW 或 NAND 本身。

| 测试工具      | fio                               |
| IO Engine | libaio                            |
| Direct IO | 开启                                |

### 二、异常现象的技术分析

### 1\. IO Size 与内部 Mapping 粒度不匹配

重点怀疑方向

这是目前最值得调查的方向之一。

假设 FW 内部以 4KB 作为 Mapping Unit，而主机使用不同 IO Size：

| Host IO Size | 与 4KB Mapping Unit 的关系   |
| ------------ | ------------------------ |
| 1KB          | 一个请求通常只覆盖部分 Mapping Unit |
| 3KB          | 一个请求可能跨越两个 Mapping Unit  |
| 4KB          | 与 Mapping Unit 对齐        |
| 8KB          | 一个请求覆盖两个 Mapping Unit    |
| 64KB         | 一个请求覆盖多个 Mapping Unit    |

不同 IO Size 可能造成不同的 FTL 处理开销。

以 3KB 为例：

* 第一个请求覆盖 0～3KB；

* 第二个请求覆盖 3～6KB；

* 第三个请求覆盖 6～9KB。

假设内部 Mapping Unit 是 4KB，那么 Host Write 会不断跨越 Mapping Unit 边界。

FW 可能需要执行：

* Host Request Splitting；

* Mapping Lookup；

* Sub-page Valid Bitmap 更新；

* DRAM Buffer 数据合并；

* 多个内部子请求的完成管理。

如果 FW 对非典型 IO Size 的处理效率不高，就可能增加请求处理时间和内部队列占用。

但必须明确：

Mapping Unit 不匹配并不必然产生 RMW。

如果 FW 使用细粒度映射、有效数据位图和 DRAM Buffer，可以避免直接读取旧数据再合并。

因此，目前不能仅凭 3KB 的异常就认定发生了 RMW。

### 2\. NAND Page 编程与 Host IO 粒度不匹配

假设 NAND Page Size 为 16KB，那么不同 Host IO Size 可能产生不同的数据聚合效率。

| Host IO Size | 聚合到 16KB 所需请求数          |
| ------------ | ----------------------- |
| 1KB          | 16                      |
| 3KB          | 需要跨请求聚合，16KB 不能被 3KB 整除 |
| 4KB          | 4                       |
| 8KB          | 2                       |
| 64KB         | 1 个请求覆盖 4 个 Page        |

这里有一个值得注意的现象：

3KB 和 8KB 都表现出明显的长尾延迟，而 4KB 相对正常。

如果 FW 的数据组织、Buffer 管理和 NAND Program 调度存在粒度相关的效率问题，就可能出现这种差异。

但 8KB 本身是 4KB 的整数倍，因此它的异常不能简单归结为非 4KB 对齐。

更值得研究的是：

* 一个 Host Request 是否被拆分成多个 NAND 子请求；

* 不同子请求是否分布在不同 Channel 或 Die；

* FW 是否需要等待多个子请求全部完成；

* 多个子请求是否产生额外的调度和资源竞争。

特别是 8KB 的长尾异常，说明问题可能涉及请求拆分、NAND Page 组织或 FW 调度，而不仅仅是地址对齐。

### 3\. SLC Fold 与 Garbage Collection 造成的资源竞争

重点怀疑方向

这款 SSD 在测试前已经经过全盘随机写预处理。

这意味着它不是一个简单的 FOB 状态设备，而是在存在大量有效数据的情况下进行后续写入。

测试过程中，SSD 可能需要同时处理：

* Host Write；

* SLC Cache 接收；

* SLC Fold 到 TLC；

* Garbage Collection；

* NAND Block Erase；

* FTL Mapping 更新。

这些操作会竞争有限的 NAND Channel、Die、Plane 和控制器资源。

当后台 Fold 或 GC 与前台写入发生资源竞争时，可能造成：

* Host Write 排队；

* NAND Channel Busy；

* Die 长时间不可用；

* FW 内部请求等待；

* 最终形成长尾延迟。

3KB 和 8KB 纯写分别出现 147.849ms、109.576ms 的 P99.9999 延迟，值得调查是否存在这种后台操作阻塞。

不过，现有数据还不能证明是 GC 或 Fold 导致的。

尤其需要注意，预处理方式是 16KB 全盘随机写，后续测试是顺序写，两者的 FTL 状态转换可能影响结果。预处理 30 分钟也不等于已经证明 SSD 达到稳态。

### 4\. SATA NCQ 队列与高并发请求调度

需要确认的系统因素

你的配置是：

```text
numjobs=1
iodepth=128
ioengine=libaio
direct=1
time_based=1
runtime=3600
```

但 SATA NCQ 的设备端队列深度通常最大为 32。

因此，QD128 不代表设备内部可以同时执行 128 条 SATA 命令。

可能的请求路径是：

```text
fio
  |
Linux Block Layer
  |
libata / SCSI
  |
AHCI Driver
  |
SATA NCQ Queue
  |
SSD Controller FW
  |
NAND Scheduler
  |
NAND
```

当主机提交的请求超过设备端 NCQ 队列容量时，额外请求需要在主机侧等待。

这会带来两个问题：

* 主机侧排队延迟可能增加；

* SSD 内部处理能力不足时，队列积压会进一步放大延迟。

但 NCQ 队列深度本身是各个 IO Size 共享的条件，不能单独解释为什么 3KB、8KB 异常而 4KB 相对正常。

因此，我认为它更可能是放大因素，而不是唯一根因。

### 三、混合读写测试揭示的另一个问题

这是我认为整组数据中非常重要、但容易被忽略的一点。

3KB、70% Read 混合负载：

| 请求类型  | P99 实测   | 标准  | 超标倍数  |
| ----- | -------- | --- | ----- |
| Read  | 11.730ms | 6ms | 1.96x |
| Write | 11.075ms | 9ms | 1.23x |

1KB、70% Read 混合负载：

| 请求类型  | P99 实测   | 标准  | 超标倍数  |
| ----- | -------- | --- | ----- |
| Read  | 10.682ms | 5ms | 2.14x |
| Write | 10.027ms | 7ms | 1.43x |

这说明读请求也受到了明显影响。

正常情况下，NAND Read 和 Program 操作可以在不同 Die、Channel 上并行执行，但实际并行程度受 NAND 架构和 FW 调度策略限制。

当写入负载持续占用资源时，读请求可能受到以下因素影响：

* NAND Channel 被写入操作占用；

* Die 正在执行 Program 或 Erase；

* FW 对读写请求的调度不合理；

* GC 搬迁数据时占用 NAND Read 资源；

* SLC Fold 与前台 Read 发生资源竞争。

这里有一个值得注意的判断：

如果纯读测试正常，而混合读写中的 Read P99 明显恶化，那么问题就不能仅从写入路径分析，还应该调查写入操作对读取服务能力的影响。

这也是企业级 SSD QoS 的重要要求：不仅要有足够的写入性能，还要在读写资源竞争时维持可预测的响应时间。

### 四、为什么 P99 和 P99.999999 都需要关注？

你这组数据中，3KB 纯写的延迟分布尤其值得研究。

3KB 纯写：延迟分布关键点

注意：不同百分位的标准不同，图表用于展示实测与标准的差距，并非同一延迟阈值。

这里可以看到：

* P99 已经达到 18.481ms，说明不只是极少数请求出现异常。

* P99.99 为 29.491ms，刚刚超标。

* P99.9999 突然上升到 147.849ms。

* P99.999999 进一步达到 212.860ms。

这呈现出比较明显的长尾延迟特征。

从工程角度看，我会将它分为两个问题：

问题 A：整体延迟偏高。

P99 已经超标 2.05 倍，可能涉及持续请求处理效率、主机排队和设备内部调度。

问题 B：极端长尾延迟。

P99.9999 和 P99.999999 明显恶化，可能涉及某些请求长时间等待 NAND 资源、后台任务阻塞或异常重试。

但这里还有一个统计学问题需要说明：

P99.999999 对应一亿个请求中的百万分之一？更准确地说，是一亿个请求中最慢的一个请求所对应的百分位附近。

因此，需要检查每个 Case 的实际完成 I/O 数量，以及 fio 是否使用了足够大的延迟统计样本。

3600 秒的运行时间并不能自动保证 P99.999999 统计可靠。假设实际 IOPS 只有 1000，那么一个小时只有 360 万次 I/O，根本不足以可靠估计这个百分位。

另外，极端百分位还要检查 fio 的直方图精度、采样方式和延迟统计配置。

因此，建议把 P99、P99.99 作为当前主要判断依据，把 P99.9999 和 P99.999999 作为需要进一步验证的极端长尾证据。

### 五、现有预处理方法是否真正达到 Steady State？

这里我还想指出一个可能影响 FA 结论的问题。

你的预处理是：

```text
16KB
100% Random Write
Full Drive
447GiB
约 30 分钟
```

这个方法确实比直接在 FOB 状态下测试更接近稳态测试，但还不能仅凭预处理时间和写入量证明已经达到严格意义上的 Steady State。

通常还需要关注：

* IOPS 是否进入稳定区间；

* 平均延迟是否趋于稳定；

* 写放大是否趋于稳定；

* GC 和 SLC Fold 是否进入相对稳定的循环；

* 预处理结束后是否进行了充分的空闲等待。

尤其是最后一点。

如果预处理结束后马上开始 QoS 测试，后台 GC 和 Fold 可能还在继续运行。

这时测试结果可能混入预处理遗留的后台任务。

建议记录预处理结束后的 NAND Busy、GC、Fold 状态，或者至少对比立即测试和充分 Idle 后测试的结果。

这对于区分 NAND 本身的性能问题与后台任务干扰很重要。

### 六、根因假设及优先级

结合所有现有信息，我建议把 FA 的根因假设分成三个层级。

| 优先级 | 根因假设                     | 支持现象                | 当前证据强度    |
| --- | ------------------------ | ------------------- | --------- |
| 1   | FW 请求拆分、合并及调度效率不足        | 3KB、8KB 异常，4KB 相对正常 | 中等        |
| 2   | NAND 资源竞争及后台任务阻塞         | 纯写出现百毫秒级长尾          | 中等        |
| 3   | SLC Fold / GC 对前台 IO 的干扰 | 全盘预处理后的持续写入         | 中等偏低      |
| 4   | SATA NCQ 与主机队列调度         | QD128，设备端 NCQ 深度有限  | 中等偏低      |
| 5   | RMW 引起额外 NAND Read       | 3KB 非典型粒度           | 较低，尚无直接证据 |

这里需要区分两个概念：

* 直接触发因素：可能是请求拆分、映射更新、NAND 资源竞争等。

* 放大因素：可能是 QD128、GC、Fold，以及主机侧队列积压。

我的初步假设是，这几个因素可能同时存在，而不是一个独立原因造成所有异常。

### 七、建议的后续 FA 验证方案

我建议不要一开始就要求 FW 团队修改代码，而是先通过实验确定异常边界。

### 第一阶段：主机侧验证

优先执行

| 实验  | 变量                                    | 目的              |
| --- | ------------------------------------- | --------------- |
| 1   | 3KB / 4KB / 8KB，QD32                  | 排除极高 QD 的影响     |
| 2   | 3KB，QD1/4/8/16/32/64/128              | 找到并发异常拐点        |
| 3   | 2KB / 3KB / 4KB / 6KB / 8KB / 12KB    | 观察 IO 粒度相关性     |
| 4   | 3KB，100% Read / 70% Read / 100% Write | 识别读写资源竞争        |
| 5   | 64KB，100% Write                       | 观察大 IO 下的持续写入能力 |

特别建议增加 6KB 和 12KB。

如果 FW 的 Mapping Unit 恰好为 4KB，那么 12KB 的请求边界可以始终落在 4KB 边界上。

它可以帮助验证非对齐因素，但仍然不能单独证明 RMW。

### 第二阶段：FW 内部数据收集

这是最重要的一阶段。

如果可以让控制器 FW 团队提供 Debug Log，我建议重点收集：

| 模块             | 需要的数据                                      | 分析目的         |
| -------------- | ------------------------------------------ | ------------ |
| Host Interface | NCQ Queue Depth、Command Latency            | 判断命令是否在接口侧排队 |
| FTL            | Mapping Lookup Latency、Mapping Cache Miss  | 判断映射开销       |
| Buffer         | Buffer Occupancy、Flush、Merge Count         | 判断数据合并效率     |
| NAND           | Read/Program/Erase Latency                 | 判断 NAND 操作耗时 |
| NAND Scheduler | Channel Busy、Die Busy                      | 判断资源竞争       |
| GC             | GC Trigger、GC Duration、Valid Page Count    | 判断垃圾回收影响     |
| SLC            | Fold Trigger、Fold Duration、Cache Occupancy | 判断缓存折叠影响     |
| FW Scheduler   | Queue Depth、Wait Time、Task Latency         | 判断调度阻塞       |

其中，我最希望获得的是三个时间：

* Host Command 到达 FW 的时间；

* FW 向 NAND 发出命令的时间；

* NAND 操作完成并向 Host 返回命令的时间。

通过这三个时间点，可以把延迟拆解成：

T_{\\text{total}} =
T_{\\text{FW queue}}+
T_{\\text{NAND wait}}+
T_{\\text{NAND operation}}+
T_{\\text{completion}}

实际实现中还需要考虑数据传输、DMA 和接口调度等阶段，但这个模型足以作为初步分析框架。

如果发现 NAND 操作本身只需要几百微秒，而 FW Queue Wait 达到几十毫秒，那么就应该重点调查 FW 调度，而不是直接归因于 NAND。

### 第三阶段：确认是否存在 RMW 和写放大

如果可以获得 NAND Read/Program 计数器，建议分别记录：

* Host Write Bytes；

* NAND Program Bytes；

* NAND Read Bytes；

* GC Copy Bytes；

* SLC Fold Bytes。

计算写放大：

WAF=\\frac{\\text{NAND Program Bytes}}{\\text{Host Write Bytes}}

然后比较 3KB、4KB、8KB 的 WAF。

如果 3KB 的 WAF 明显高于 4KB，说明它可能产生了额外的数据搬迁或编程开销。

但是 WAF 高并不直接证明 RMW，还需要结合 NAND Read Count 和 FW 的内部请求日志判断。

### 八、建议的 FA 结论

如果现在必须给出一份阶段性 FA 结论，我建议采用下面这段表述。

# 480GB SATA TLC SSD QoS 异常阶段性 FA 结论

## 1. 异常描述

在 480GB SATA TLC SSD 的 QoS 测试中，设备经过 16KB、100% Random Write 全盘预处理后，使用 fio 进行持续读写测试。测试采用 libaio、direct IO，单 Job、QD128，单项运行时间为 3600 秒。

测试结果显示，部分 IO Size 和读写负载组合存在 QoS 不达标现象。其中，3KB 和 8KB 纯写场景的长尾延迟异常较为突出：

- 3KB 纯写 P99.9999 达到 147.849ms，超过标准 3.79 倍；
- 3KB 纯写 P99.999999 达到 212.860ms，超过标准 5.07 倍；
- 8KB 纯写 P99.9999 达到 109.576ms，超过标准 2.15 倍；
- 8KB 纯写 P99.999999 达到 175.112ms，超过标准 3.30 倍。

同时，1KB 和 3KB 的 70% Read 混合负载中，Read P99 也出现明显超标。

## 2. 初步原因分析

根据现有测试结果，初步认为异常可能与 SSD 在特定 IO Size 和高并发条件下的内部请求处理及资源调度效率有关。

主要怀疑方向如下：

1. **FTL 请求处理开销：** 非典型 Host IO Size 可能增加内部请求拆分、Mapping 更新及数据合并开销，导致 FW 调度效率下降。

2. **NAND 资源竞争：** 高并发持续写入可能导致 NAND Channel、Die 等资源竞争，增加前台请求等待时间。

3. **后台任务干扰：** SLC Fold、Garbage Collection 等后台操作可能与前台 Host IO 争抢 NAND 资源，造成长尾延迟。

4. **主机接口及队列调度：** QD128 高于 SATA 设备通常支持的 NCQ 队列深度，主机侧排队及设备内部调度可能进一步放大延迟。

此外，3KB 非 4KB 对齐写入可能增加 FTL 数据组织复杂度，但目前没有直接证据证明存在 RMW 行为。

## 3. 后续验证建议

建议进一步开展以下工作：

- 对比不同 IO Size 和不同 QD 下的 QoS 表现，明确异常与 IO 粒度、并发深度之间的关系；
- 获取 FW 内部 Request Queue、Mapping、Buffer、NAND Scheduler 等模块的运行数据；
- 监控 NAND Channel/Die Busy、GC 和 SLC Fold 状态，确认是否存在后台任务引起的前台 IO 阻塞；
- 统计 NAND Read/Program 数据量，分析是否存在额外的数据搬迁和写放大；
- 进一步确认预处理是否达到稳定状态，并验证极高延迟百分位的统计可靠性。

## 4. 阶段性结论

目前测试结果表明，该 SSD 在部分小粒度及中等粒度高并发写入场景下存在明显的 QoS 长尾延迟异常，且混合读写负载下的读请求也受到一定影响。

现阶段倾向于从 FW 内部请求处理、NAND 资源调度及后台维护任务三个方向开展进一步分析。

目前尚缺少控制器内部日志和 NAND 操作时序数据，暂不能将异常明确归因于 FTL、GC、SLC Fold 或 NAND 本身，具体根因仍需通过进一步实验和 FW 内部数据验证。

### 九、我个人认为最值得投入精力的地方

如果我是这个问题的 EFA，我不会首先去怀疑 NAND Die 的质量，也不会直接要求 FW 修改 RMW 逻辑。

我会优先做一件事：

把 3KB、4KB、8KB 三种测试的 Host IO 与 NAND 实际操作建立对应关系。

原因很简单：

* 4KB 纯写基本正常；

* 3KB 纯写严重异常；

* 8KB 纯写同样严重异常；

* 混合负载中 Read 也会受到影响。

这组现象更像是一个涉及 FTL、NAND 调度和后台任务的系统级问题。

我尤其想知道，3KB 和 8KB 测试时，FW 是否发生了大量内部请求拆分，以及这些请求是否在 NAND Scheduler 中产生了长时间等待。

另外，有两个信息目前仍然缺失，正式结论前必须补齐：

* 64KB 的实际测试结果。不能因为没有出现在 FAIL 列表中就直接认定全部 PASS。

* SSD 的逻辑扇区大小，以及实际 fio 延迟统计样本量。尤其是 P99.999999，必须确认统计可靠性。

最终判断：目前可以确认的是特定 IO Size、高并发持续写入场景下存在严重 QoS 异常；不能确认的是异常究竟来自 FTL、FW 调度、NAND 资源竞争还是后台 GC/Fold。

我认为这份 FA 最有价值的突破口，就是从主机侧延迟分布向下追踪到 FW Queue Wait 和 NAND Busy 时间。这样才能把一个 QoS 不合格的问题，真正转化为可定位、可复现、可修复的技术问题。
